## ADDED Requirements

### Requirement: test-plan artifact generation
specpower plan shall generate `specpower/changes/<change-name>/test-plan.md` when the change's delta specs contain at least one Scenario (i.e. introduce or modify testable behavior). When the delta specs have no Scenario, `test-plan.md` is **optional** — it may carry only baseline-regression Cases (e.g. a pure refactor that touches existing code but does not change specs); pure documentation/config changes (no Scenario and no code touched) shall not create one. The file shall be generated during the plan flow alongside `proposal.md`, delta `specs/`, `design.md`, and `tasks.md`, as the first draft for subsequent `refine` iteration.

#### Scenario: testable change (delta scenario) must create test-plan
- **WHEN** the change generated by plan has at least one Scenario in its delta specs
- **THEN** `test-plan.md` exists in the change directory before plan completes

#### Scenario: change with no delta scenario may optionally carry a baseline-regression test-plan
- **WHEN** the change generated by plan has no Scenario in its delta specs but touches existing code (e.g. a pure refactor)
- **THEN** a `test-plan.md` may optionally be generated, containing only baseline-regression Cases; its absence does not report a warning (the delta coverage rule is vacuously satisfied at this point)

#### Scenario: pure documentation/config change does not create test-plan
- **WHEN** the change generated by plan has no Scenario and touches no code (pure docs, config-only, pure rename)
- **THEN** `test-plan.md` is not created and the tool shall not require its existence

#### Scenario: delta-scenario change missing test-plan is reported (missing)
- **WHEN** the change's delta specs contain a Scenario but there is no `test-plan.md` at validate/verify time
- **THEN** the tool reports a warning naming the change (not an error, to stay compatible with existing changes that predate this capability)

### Requirement: test-plan Case format
Each entry ("Case") in `test-plan.md` shall be machine-parseable and: carry a stable, change-unique `id:` (e.g. `T1`, unrelated to the `it()` name); reference exactly one spec Scenario by name (a delta Scenario or a baseline-regression Scenario); declare a `[positive]`/`[negative]` classification; state the input and expected result; and propose an `it()` test name. The token embedded in test code shall be **globally unique** — carrying the change prefix `<changeName>-<id>` (e.g. `[add-test-plan-artifact-T3]`), so that when multiple changes coexist, same-number tokens do not collide and verify cannot distinguish them. A Case shall reference a Scenario by name rather than copying its `WHEN`/`THEN` body, keeping the spec the single source of behavioral intent.

#### Scenario: valid Case
- **WHEN** a Case is written
- **THEN** it carries a stable unique `id:`, references a Scenario by name, carries a `[positive]`/`[negative]` marker, contains input and expected, and proposes an `it()` name

#### Scenario: Case without stable id is rejected (reject)
- **WHEN** a Case has no `id:` (or the id is duplicated within the change)
- **THEN** validation fails and reports the Case

#### Scenario: Case id is stable and never renumbered
- **WHEN** `refine` adds/merges/edits Cases across rounds, or `plan`/`refine` regenerates `test-plan.md`
- **THEN** existing Case `id:`s shall not be renumbered or reused; merged Cases keep one of their original ids; on regeneration, the old file is read and existing ids preserved, allocating only to new Cases; the change prefix is stable (the change name does not change)

#### Scenario: embedded token is globally unique with change prefix
- **WHEN** multiple changes coexist, each with a Case `T1`
- **THEN** the token embedded in test code is `<changeName>-T1` (different for each), and verify can distinguish each change's cases with no collision and no false report

#### Scenario: change name globally unique (including archived) guarantees prefix non-collision
- **WHEN** the name given to `specpower change new <name>` is already used (in-flight or within `archive/`)
- **THEN** creation is rejected with a prompt to rename, so that the `<changeName>-` prefix is globally unique and an archived old change's tests do not collide with a new change's tokens

#### Scenario: Case with no scenario reference is rejected (reject)
- **WHEN** a Case references no spec Scenario
- **THEN** validation fails and reports the orphan Case

#### Scenario: Case may reference a baseline scenario as regression
- **WHEN** a Case references a Scenario that exists in `specpower/specs/` (baseline) rather than the delta specs
- **THEN** the Case is accepted as a regression Case (the coverage rule still applies only to delta Scenarios)

#### Scenario: Case referencing a non-existent scenario is rejected (reject)
- **WHEN** a Case references a Scenario name that exists in neither the delta specs nor `specpower/specs/`
- **THEN** validation fails and reports the Case and the missing Scenario

#### Scenario: duplicate it() name within a change is rejected (duplicate)
- **WHEN** two Cases in the same change propose the same `it()` name
- **THEN** validation fails and reports the duplicate

### Requirement: scenario→Case coverage
Every Scenario in the change's delta specs shall have at least one Case in `test-plan.md`. Every Requirement that admits failure (behavior with side effects, IO, state, or contract validation) shall have at least one negative Case covering a contract violation or exceptional input/precondition, following the positive/negative distinction in `prompts/reference/specpower/negative-testing-guide.md`. Legitimate boundary values the contract accepts (empty collection, extremes, large input) shall be classified as `[positive]`, not labeled `[negative]`.

#### Scenario: fully-covered change passes validation
- **WHEN** every Scenario has at least one Case and every failure-admitting Requirement has at least one negative Case
- **THEN** validation passes with no coverage errors

#### Scenario: uncovered scenario fails validation (fail)
- **WHEN** a Scenario has no Case in `test-plan.md`
- **THEN** validation fails and reports the uncovered Scenario

#### Scenario: failure-admitting Requirement missing negative case fails validation (missing)
- **WHEN** a Requirement admits failure (side effects/IO/state/contract validation) but has no negative Case
- **THEN** validation fails and reports the Requirement and the missing negative dimension

#### Scenario: mislabeled-negative boundary Case (wrong) is a review item, not auto-rejected
- **WHEN** a Case is marked `[negative]` but its input is a legitimate boundary value within the contract (e.g. the function accepts an empty collection as valid input)
- **THEN** the validator shall not automatically reject (it does not judge classification semantics); misclassification is flagged as a `refine`/review check item, not a validation error

### Requirement: test-plan lifecycle
`test-plan.md` shall be archived with the change by `specpower done` and shall not be merged into the baseline `specpower/specs/`. It shall be iterable in `refine` (add/merge/edit Cases while preserving Scenario references and `id:` stability), consumed as a case list by `build` Phase B (TDD), and cross-checked by `verify`.

#### Scenario: done archives but does not merge
- **WHEN** `specpower done` archives a completed change
- **THEN** `test-plan.md` goes into the change archive and is not merged into `specpower/specs/`

#### Scenario: refine iterates Cases
- **WHEN** `specpower refine` runs on a change containing `test-plan.md`
- **THEN** refine may add/merge/edit Cases across rounds, preserving each Case's Scenario reference and `id:` stability

#### Scenario: rename-scenario atomically renames a baseline scenario and syncs references
- **WHEN** `specpower rename-scenario <cap> <old> <new>` is run
- **THEN** the Scenario name in baseline `specpower/specs/<cap>/spec.md` is changed, and all Cases referencing the old name in in-flight + archived `test-plan.md` are synced to the new name; the operation supports `--dry-run` to preview affected files, requires confirmation, and relies on git reversibility

#### Scenario: archived test-plan's baseline reference does not silently dangle
- **WHEN** a baseline Scenario is renamed and an archived test-plan references the old name
- **THEN** `rename-scenario` syncs that archived test-plan's reference; absent sync, the reference shall not silently fail (rejecting a bare edit of the baseline spec name outside `rename-scenario`)

#### Scenario: rename-scenario rejects a non-existent scenario (reject)
- **WHEN** `specpower rename-scenario` targets a Scenario name that does not exist in the baseline spec
- **THEN** the operation fails with an error naming the missing Scenario and writes nothing

#### Scenario: build Phase B consumes Cases via id-embedded it()
- **WHEN** `specpower build` Phase B runs TDD on a change containing `test-plan.md`
- **THEN** each Case drives an `it()` test whose name embeds the **globally-unique change-prefixed token** (e.g. `it('throws on unknown [add-test-plan-artifact-T3]', …)`), named by the Case's planned name; a `[negative]` Case produces a test reproducing a contract violation

#### Scenario: verify runs two-step coverage check
- **WHEN** `specpower verify` runs on a built change
- **THEN** Step1 scans the test suite for every Case's **prefix token** (`<changeName>-Tn`); if missing it fails (fail) and names the Case (no omission, no cross-change false report); Step2 reads each located `it()`'s code and verifies its semantics match the Case's definition — the test calls the function under test with the Case's `Input` and asserts the Case's `Expected` outcome; a mismatch (the test asserts a different outcome than the plan) fails (fail); when the correspondence genuinely cannot be determined it reports a warning

#### Scenario: archiving a testable change without test-plan is blocked
- **WHEN** `specpower done` is asked to archive a change that has a (delta) Scenario but lacks `test-plan.md`
- **THEN** archiving is blocked and reports the change (unless `--force` is passed)

### Requirement: validation integration
When `specpower validate` validates a spec file that belongs to a change directory containing `test-plan.md`, it shall parse `test-plan.md` and enforce the scenario→Case coverage and negative-case rules above. When the spec belongs to a testable change lacking `test-plan.md`, validation shall emit a warning (not an error); under `--strict`, that warning shall be upgraded to an error.

#### Scenario: compliant test-plan passes validation
- **WHEN** `specpower validate <spec>` runs on a spec whose change directory's `test-plan.md` covers all Scenarios and contains the required negative cases
- **THEN** validation returns valid, with zero errors and zero warnings

#### Scenario: coverage gap fails validation (fail)
- **WHEN** `specpower validate <spec>` runs and some Scenario has no Case in the change's `test-plan.md`
- **THEN** validation returns invalid and reports the uncovered Scenario

#### Scenario: strict mode upgrades missing-file warning
- **WHEN** `specpower validate --strict` runs on a spec belonging to a testable change lacking `test-plan.md`
- **THEN** the missing-file case is reported as an error rather than a warning
